# Arquitectura de código FranToken

Usá [Code Architecture](../../../docs/architecture/CODE-ARCHITECTURE.md) como contrato de organización de código y [AGENTS.md](../../../AGENTS.md) para la precedencia del proyecto. Aplicá este skill al crear, mover o revisar módulos de `src/`; para contenido y diseño de la web, combiná con [frantoken-web](../frantoken-web/SKILL.md). Consultá [Business Logic](../../../docs/business/BUSINESS-LOGIC.md) cuando una regla de negocio afecte el código.

Ubicá la implementación en la feature que la necesita. Guardá listas y configuración estática en `features/<nombre>/constants/`, tipos en `types/` y funciones puras propias en `utils/`; no declares tipos en archivos de constantes ni llenes el componente o contenedor con esos bloques. Si la feature necesita servicios, adapters, modelos o repositorios, crealos **dentro de ella**; elevá a `core/` solo contratos realmente compartidos. Mantené la ruta Next.js fina y el acceso externo detrás de repositorios/adapters. No crees capas o archivos vacíos para completar un árbol teórico.

Importá la vista directamente desde la ruta cuando solo hay render o interacción visual. Creá `*.container.tsx` únicamente para fetching, coordinación de servicios/hooks, flags, transformación de datos dinámicos o decisiones de negocio. Un contenedor que solo devuelve la vista o le pasa constantes estáticas sobra. La vista compone JSX/HTML, recibe props si hacen falta y puede manejar estado visual efímero o Motion; no ejecuta reglas de negocio. Respetá la aclaración del usuario: “HTMX” significa JSX/HTML presentacional sin lógica de negocio, no la dependencia HTMX.

Al crear o modificar UI, componé estilos con utilidades Tailwind. En `src/app/globals.css` dejá la entrada de Tailwind, tokens/variables, fuentes y base global mínima; no escribas CSS de secciones o componentes ni CSS Modules. Diseñá movimiento vistoso y coherente con la página usando `motion/react`, con una secuencia principal y microinteracciones cuidadas. Respetá movimiento reducido, accesibilidad y lectura de información crítica. Aislá los Client Components donde Motion o la interacción realmente los requieran. Consultá el contrato de [estilos y movimiento](../../../docs/architecture/CODE-ARCHITECTURE.md#estilos-y-movimiento-de-la-ui) antes de implementar una pantalla.

Leé [UI Contract](../../../docs/design/UI-CONTRACT.md): cabecera, pie, banner y controles atómicos se reutilizan entre rutas; iconos provienen de `lucide-react`; cada pantalla tiene skeleton. Si hay mocks sin fetching, simulá una carga breve en un servicio de demo; con fetching real, usá su estado sin demora artificial. Si una primitiva compartida existente necesita cambios, consultá al usuario antes de editarla y ofrecé variante con `clsx`, componente nuevo o cambio común. Podés avanzar con trabajo independiente mientras llega la respuesta.

Aplicá las reglas de sufijos y de nombres React del documento de arquitectura. Usá barrels explícitos solo en carpetas compartidas; nunca en `features/`. Preservá los nombres especiales de Next.js. Antes de escribir código Next, consultá la guía pertinente en `node_modules/next/dist/docs/`. Verificá las convenciones mecánicas con `node scripts/check-architecture.mjs` y revisá manualmente límites de dependencias, necesidad de contenedores, ubicación de constantes/utilidades, Tailwind y calidad visual del movimiento.
